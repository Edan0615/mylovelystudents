Part 02. 資料表在 UI/UX 的視覺具現化

用設計師的眼睛閱讀資料庫

後台最核心的介面元件是「資料表格 (Data Table)」。這並不是設計師隨意排版的成果，而是後端資料庫中「資料表」結構在前端的鏡像對接。

直欄 (Columns) = UI 表頭與欄位

資料庫裡的 user_name、created_at 等直欄，直接對應為 UI 表格上方的「表頭標題列」。設計師需依據欄位屬性決定寬度、對齊（如數字靠右對齊，文字靠左對齊）與截斷規範。

橫列 (Rows) = UI 資料列表

資料庫中每新增一筆使用者記錄，在前端表格中就會多出一條「橫列」。這就是為什麼需要設計「分頁機制 (Pagination)」或「無限滾動」，避免一次載入太多資料列導致效能崩潰。

主鍵 (Primary Key) = 跳轉核心

主鍵是資料的唯一身分標識。在 UI 上，主鍵通常做為超連結或操作按鈕。點擊「查看詳情」或「編輯」時，前端將攜帶這個 ID 去向後端 API 請求該筆資料的完整表單。

Part 03. 後台管理系統經典佈局與表單心理學

三欄式架構佈局 & 增刪查改 (CRUD) 防呆設計

後台系統的核心任務是協助管理者「快速做出正確決策與資料處理」。這需要符合兩大設計主軸：高資訊密度的經典佈局，與防止使用者輸入錯誤資料的表單心理學。

表單防呆心理學：視覺防錯設計

後端資料庫（如 SQL）非常嚴格。如果一個欄位在資料庫規定只能存「整數」，而使用者在前端輸入了「中文字」，後端在寫入時就會噴出嚴重的 SQL 語法錯誤 (TypeError) 甚至導致崩潰。

UI/UX 設計師的任務就是透過「視覺限制」進行防錯。例如：使用下拉選單 (Dropdown) 代替文字輸入框、用日曆選擇器限制日期格式、在送出按鈕加上即時的欄位格式驗證，確保進到後端資料庫的資料是 100% 格式正確的。

即時防錯表單模擬

❌ 名稱長度不合規範或包含特殊符號！
❌ 日期格式不符合 yyyy-mm-dd 規範！
Part 04. Figma 實務奠基：後台自適應網格規範

後台系統高資訊密度的 12 欄網格與 RWD 實務

管理系統後台通常會有大量複雜的數據卡片和圖表。如何在有限且不固定的螢幕寬度下，維持資訊的對齊與呼吸感？這就必須仰賴 12 欄網格系統 (12-Column Grid System) 與自適應 (Responsive Web Design, RWD) 的思考模型。

Figma 與前端 RWD 的換算邏輯

  • 12 是最完美的公約數：因為 12 可以被 1, 2, 3, 4, 6 整除。這代表一個版面可以被均分為 2 欄 (各佔 6 欄)、3 欄 (各佔 4 欄) 或 4 欄 (各佔 3 欄)，對後台極具彈性。
  • 斷點 (Breakpoints) 與自適應：在 Figma 中，我們需要分別建立 Desktop (1440px)、Tablet (768px) 與 Mobile (375px) 的基礎畫布，並確保元件能在不同欄數下伸縮自如。
