Chapter 04 · What is BaaS

認識你用過的 BaaS

BaaS 是 Backend as a Service（後端即服務）的縮寫，念作「貝斯」。意思是：後端不用自己寫、自己架，而是把它當成一項「現成的服務」來租用。

為什麼叫 BaaS？

把「後端」變成可租用的服務

一個完整網站需要：資料庫、會員登入、檔案儲存、API、權限控管。傳統做法要自己寫程式、架伺服器。BaaS 把這些後端功能預先做好，包成服務，開發者只要在前端呼叫 SDK 就能使用。

名稱沿用雲端運算 XaaS 的命名邏輯，例如 SaaS（軟體即服務）、IaaS（基礎設施即服務），這裡的 X 就是 Backend。

生活比喻

自己開餐廳要買地、蓋廚房、請廚師（自建後端）；BaaS 像是進駐共享廚房，設備與廚師都備好，你只要專心設計菜單與出餐（前端）。

Supabase 提供了什麼

Chapter 06 · Architectural Pain Points

為什麼不能停留在純 BaaS 模式

01

商業邏輯分散，維護不易

邏輯散落在前端 Vue 元件與資料庫 SQL Trigger 之間，面對多重折扣、庫存風控等複雜邏輯時除錯極難。

02

金流私鑰與機密資料風險

串接綠界等金流時，HashKey/HashIV 等私密金鑰不能放在前端，必須由獨立的 Application Server 集中處理。

03

無法應對私有化部署（On-Premise）

企業客戶與公部門因法規無法將資料放在第三方雲端平台，必須具備在獨立 Linux 伺服器自建 API 與資料庫的能力。

Chapter 07 · Why Laravel

為什麼選擇 Laravel？

從技術完整度、商業接案優勢與生態系深度三個角度，為什麼 Laravel 是接案型全端工程師的高效率選擇。

01

生態系與套件庫極度龐大

開箱即用，拒絕重複造輪子

  • Composer 與 Packagist：綠界 / 藍新金流、電子發票、PDF 報表、Excel 匯入匯出、簡訊驗證、圖表統計等需求，社群多半已有成熟套件可用，能把數週的開發時程壓縮很多。
  • Filament 後台：不用從零手刻管理後台，幾行 PHP 就能長出美觀、安全的 Admin 介面，大幅降低交付成本。
02

SEO 友善與行銷支援

中小企業客戶最在意的商業價值

  • 純 CSR 的前端 SPA 對搜尋引擎爬蟲較不利。
  • Laravel 可由伺服器輸出頁面，搭配套件輕鬆產生動態 Meta Tags、OpenGraph 社群預覽與 XML Sitemap。
  • 能兼顧「前台 Vue 的流暢互動」與「搜尋引擎的最佳化結構」。
03

內建現代全端基建

Batteries-Included

  • 認證與授權：內建登入機制與 Breeze 腳手架，免去手刻 Session 與防護的繁瑣。
  • Eloquent ORM：寫法優雅直覺，輕鬆處理一對多、多對多關聯。
  • Queue 與 Task Scheduling：寄信、訂單逾時取消、統計報表，不用自己拼 crontab。
  • Form Request 驗證：統一資料驗證，避免髒資料進入資料庫。
04

程式碼規範度高，利於維護與交付

Convention over Configuration

  • 嚴格、標準的 MVC 慣例，目錄與命名都有約定。
  • 半年後自己回頭看，或客戶轉交給其他 Laravel 工程師，都能很快看懂結構，降低交付與售後保固成本。

Chapter 08 · Why MySQL

資料庫選型與架構升級指南

第 2 專案我們用 PostgreSQL（Supabase），第 3 專案改用 MySQL。這不是誰比較強，而是「架構不同，最佳解也不同」。

Part 1 · 技術特性客觀對比

面向PostgreSQL（第 2 專案）MySQL（第 3 專案）
設計哲學強調嚴謹標準與功能完整度強調簡單、極速與易維運
擅長場景複雜關聯聚合、分析型查詢、Serverless BaaS讀多寫少的 Web 應用（官網、電商、管理系統）
資料型態JSONB、陣列支援強大支援 JSON，但以傳統關聯式欄位為主
擴展能力豐富外掛（PostGIS、pgvector）內建功能精簡，擴展以應用層為主
權限控管內建 RLS（Row Level Security）不依賴 RLS，權限由應用層處理
普及度成長快速，社群活躍全球 Web 生態普及度極高

Part 2 · 商業與接案現實面：選擇 MySQL 的四個核心理由

01

主機與維運成本最低

中小企業客戶預算有限。常見的虛擬主機（cPanel、Hostinger）、平價 VPS、DigitalOcean，到 AWS RDS、GCP Cloud SQL，都把 MySQL 當作標配選項，門檻最低。選 MySQL 能降低客戶的長期持有成本（TCO），報價更具競爭力。

02

企業客戶交接與相容性最高

中小企業與外包市場中，絕大多數現存系統（WordPress、Laravel、舊有 ERP / CRM）都跑在 MySQL 上。掌握 MySQL 的 Schema 設計與效能優化，能無縫接軌客戶現有的資料庫伺服器，不必強迫客戶額外購買或學習 PostgreSQL 維運。

03

生態系與除錯社群極致成熟

Laravel 與 MySQL 是業界十幾年來最經典的黃金搭檔，踩坑紀錄最完整。接案最怕冷門 Bug 卡死時程，MySQL 龐大的中文與國際社群，讓突發狀況更容易在短時間內找到解法，幫助專案如期驗收交付。

04

回歸應用層架構的純粹性

上次用 PostgreSQL，是因為 Supabase 需要靠 RLS 擋權限。這次是正規企業級全端，權限校驗、商業邏輯與 API 驗證都收斂在 Laravel 中介層與 Filament 後台。資料庫回歸最純粹的高效 CRUD，MySQL 就是高效且穩健的基底。

第 2 專案：權限在資料庫

Vue → SDK → PostgreSQL（RLS / Trigger）

資料庫承擔權限與部分邏輯。

第 3 專案：權限在應用層

Vue → Axios → Laravel（Middleware）→ MySQL

資料庫專注儲存，驗證與邏輯集中在 Laravel。

Teacher Script · 老師對學員的對話引導

「柏安，上一個專案你用 PostgreSQL，那是因為 Supabase 需要靠資料庫的 RLS 來擋權限，它很適合 Serverless 的快攻。但這次我們要做的是企業級全端，權限、邏輯和驗證都會收斂在 Laravel 和 Filament，資料庫就回到最單純、最高效的資料儲存角色。而在接案現場，客戶的主機、既有系統和預算，大多都是建立在 MySQL 上，所以你學會 MySQL，就能直接接手客戶的系統，報價也更有競爭力。這不是 PostgreSQL 不好，而是在『接案賺錢』這件事上，MySQL 是最穩、最好落地的選擇。等你將來遇到需要 JSONB 或 GIS 的專案，再把 PostgreSQL 拿出來，這就是架構師跟工匠的差別——根據場景選工具。」

Chapter 09 · Admin Panel Tooling

後台工具選型：Filament vs Voyager

第 3 專案的管理後台不從零刻起，而是用 Laravel 生態的後台套件快速建立。主力採用 Filament，Voyager 作為備選評估。

Laravel Filament

主力選擇

以 Livewire + Alpine.js + Tailwind CSS 打造的現代後台框架，以程式碼定義資源（Resource）。

優點

  • 社群活躍、更新頻繁，跟上新版 Laravel
  • 表單、表格、篩選、通知等元件完整，介面現代美觀
  • 全程用 PHP 程式碼定義，易於版本控管與客製化
  • 插件生態豐富，支援多 Panel、權限與多租戶擴充
  • 不需要寫前端 JS，快速交付完整 CRUD 後台

缺點

  • 需要理解 Livewire 的運作方式，學習曲線較陡
  • 大版本升級時，客製化部分可能要調整
  • 後台自成一體，與 Vue 3 前台是兩套前端思維

Laravel Voyager

備選評估

以資料庫表格為核心的 BREAD（Browse / Read / Edit / Add / Delete）後台，偏向用介面設定。

優點

  • 安裝後可直接在介面中設定資料表，上手快
  • 內建媒體管理、選單、角色權限等功能
  • 適合快速產出簡單的內容管理後台

缺點

  • 更新與維護較不穩定，對新版 Laravel 支援可能落後
  • 設定存在資料庫中，不易版本控管與團隊協作
  • 複雜商業邏輯與深度客製化較吃力
  • 介面與生態不如 Filament 現代，長期風險較高

結論：中大型、需客製與長期維護的專案以 Filament 為首選；Voyager 僅適合極簡、短期的內容管理需求。（版本與維護狀態請於選型前再次確認官方現況。）
